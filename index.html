3. Connect GitHub to AWS

GitHub connection: GitHub via GitHub App / AWS CodeConnections.
  1. Open AWS CodePipeline.
  2. Create a new pipeline.
  3. Select Build custom pipeline.
  4. For the source provider, select GitHub (via GitHub App).
  5. Create or select the GitHub connection.
  6. Select raj-shekhar-singh09/elasticBean.
  7. Select the main branch.
  8. Use the CodePipeline default output artifact format.

The important repository format is: 

GitHubUsername/RepositoryName
raj-shekhar-singh09/elasticBean

4. Why We Used a Custom Pipeline

The initial CodePipeline template page showed Docker-oriented templates such as Push to ECR and Deploy to ECS Fargate. Those were not appropriate for this setup.

Do not use: Push to ECR, ECS Fargate, CloudFormation, or Terraform for this simple Elastic Beanstalk flow.

We selected Build custom pipeline so that the stages could be explicitly configured as Source → Staging → Manual Approval → Production.

5. Build Stage

Build stage: skipped.

The repository contains a simple HTML/PHP application and does not require compilation or packaging with Maven, Gradle, or CodeBuild. Therefore the source artifact can be passed directly to Elastic Beanstalk.

6. Test Stage

Test stage: skipped for this learning setup.

A test stage can be added later. For a real production application, automated tests should normally run before the staging deployment or before production promotion.

7. Elastic Beanstalk Staging Deployment

The first Elastic Beanstalk deploy action is the staging deployment. 

Stage name:
Deploy-Staging

Provider:
AWS Elastic Beanstalk

Application:
<existing Elastic Beanstalk application>

Environment:
<staging environment>

CodePipeline takes the source artifact from GitHub and creates an Elastic Beanstalk application version, then deploys that version to the staging environment.

8. IAM Permission Problem We Fixed

Original error:
The provided role does not have the elasticbeanstalk:CreateApplicationVersion permission.

The role that needed the permission was the CodePipeline service role, not the Elastic Beanstalk EC2/compute role. 

AWSCodePipelineServiceRole-ap-south-1-git_to_elbean

We edited the policy attached to that role and added the permissions required for the Elastic Beanstalk deployment action.

The important conceptual distinction is: 

CodePipeline
    ↓
AWSCodePipelineServiceRole-...
    ↓
Elastic Beanstalk deployment

NOT

CodePipeline
    ↓
Elastic Beanstalk Compute Role
The broad permissions used for the learning setup should be tightened to least privilege for a real production account.

9. Manual Approval Before Production

After staging succeeds, the pipeline should pause for a human decision. 

Stage:
ManualApproval

Action:
ApproveProduction

Provider:
Manual approval

Message:
Review the staging Elastic Beanstalk environment
before releasing this version to production.

Optionally provide the staging application URL as the review URL. The approver can open the staging application, test it, and then approve or reject the release.

Approve: continue to production.
Reject: stop the release; production is not updated.

10. Production Deployment

After the manual approval succeeds, add another deploy stage. 

Stage name:
Deploy-Production

Provider:
AWS Elastic Beanstalk

Application:
<same Elastic Beanstalk application>

Environment:
<production environment>

The important idea is that production receives the same pipeline source artifact that was already deployed to staging.

12. What Happens After a Git Push?

git add .
git commit -m "Update application"
git push origin main

The expected flow is:

  1. GitHub receives the commit.
  2. CodePipeline detects the change.
  3. The Source stage downloads the repository.
  4. The source artifact is deployed to Elastic Beanstalk staging.
  5. The pipeline pauses at Manual Approval.
  6. You open and test the staging application.
  7. You approve the release.
  8. The same artifact is deployed to Elastic Beanstalk production.
Result: GitHub → Staging → Human verification → Production.

13. Things We Do Not Need for This Setup

  • Second CodePipeline
  • Docker
  • Amazon ECR
  • Amazon ECS
  • CodeBuild, for the current simple HTML/PHP application
  • Another GitHub connection
  • A separate source stage for production

14. Recommended Production Improvements Later

  • Add automated tests before staging or before production.
  • Add security scanning.
  • Use least-privilege IAM policies instead of broad wildcards.
  • Use separate staging and production configuration/secrets.
  • Add monitoring and rollback procedures.
  • Consider deployment strategies such as rolling or immutable deployments.
  • Protect the production environment from accidental changes.
